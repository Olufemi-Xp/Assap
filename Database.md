## 1. Database Technology & Configuration Overview

### Engine & Query Layer
- **Primary Database:** PostgreSQL (hosted on Supabase), paired with Supabase Storage for private selfie and valid ID document uploads.
- **Query & Mutation Layer:** `@supabase/supabase-js` and `@supabase/ssr` invoked exclusively inside `src/services/**` modules, with `zod` schema validation on inputs and `src/lib/contact-sanitizer.ts` enforcing contact visibility rules on outbound DTOs. No separate external ORM is introduced in MVP.

### Naming Conventions
- **Tables:** `snake_case`, plural nouns (e.g., `users`, `provider_profiles`, `identity_records`, `subscriptions`, `ratings`, `reports`, `user_blocks`, `payment_events`).
- **Columns:** `snake_case`, singular for scalar attributes, explicit suffixes for timestamps (`_at`) and foreign keys (`_id`).
- **Primary Keys:** `UUID` (`gen_random_uuid()`) across application tables (`id` column), avoiding sequential integer enumeration of user/provider/report/payment IDs.

### Standard Audit Columns & Deletion Policy
- **Standard Audit Columns:** Every core table includes `created_at` (`TIMESTAMPTZ`, default `now()`, `NOT NULL`) and `updated_at` (`TIMESTAMPTZ`, default `now()`, `NOT NULL`). `payment_events` also records `processed_at` (`TIMESTAMPTZ`) for webhook idempotency auditing.
- **Hard Delete vs. Soft Delete (`deleted_at`):**
  - **Hard Delete:** Ephemeral/non-audit records such as `user_blocks` (when a user unblocks another user) or draft/unsubmitted temporary state may be hard-deleted.
  - **Soft Delete (`deleted_at TIMESTAMPTZ NULL`) / Status Lifecycle:** `users` and `provider_profiles` support `deleted_at` (or status flags) so historical `ratings`, `subscriptions`, `payment_events`, and `reports` maintain referential integrity and auditability without orphaning financial or safety records. `identity_records`, `subscriptions`, `payment_events`, and `reports` are never hard-deleted during normal app operations.
